## 공통 규칙

- **하나의 스파이크 = 하나의 하위 세션 = 하나의 work 폴더.** 예: `work/jadecode/<MMDD>-spike-s1-claude-driver`. 시제품 코드는 그 work 폴더 안에 두고 jadecode 레포에 커밋하지 않는다. 결과 문서만 남긴다(아래 「결과 양식」).
- **사용자 전역 설정을 건드리지 않는다.** `~/.claude/settings.json`, `~/.claude/skills`, 훅 설치 명령(`herdr integration install`, `rex skill setup` 등)을 쓰지 않는다. Claude Code 설정은 `--settings <파일>`, `--mcp-config <파일> --strict-mcp-config`, 스파이크 폴더 안의 `.claude/settings.local.json`으로만 준다.
- **사람의 구독으로 공식 `claude` 바이너리를 돌린다.** Agent SDK로 구독 로그인을 쓰지 않는다(정책 회색 지대, `questions.md` X1). 스파이크마다 사용량 상한을 브리프에 적는다(아래 「예상 비용」).
- **시간 상자.** 예상 시간의 1.5배를 넘기면 거기까지의 결과로 멈추고 보고한다. 통과 기준을 못 채운 것도 결과다.
- 하위 세션은 `cd` 대신 `git -C <경로>`와 절대 경로를 쓴다(루트 `AGENTS.md`).
- CLI 버전을 결과에 적는다(`claude --version` 등). 비대화 모드 동작은 버전마다 바뀐다.

## 결과 양식

각 스파이크는 끝날 때 자기 work의 `task.md` `## 마무리`와 별도로 `result.md` 하나를 쓴다. architecture work가 그것을 모아 `docs/architecture/spike-results.md`로 옮긴다.

```markdown
# S<n> <제목> 결과
- 도구 버전:
- 가설별 판정: H1 통과/실패/부분 — 근거(명령, 출력 발췌)
- 통과 기준 판정:
- 추천 후보에 주는 영향: (유지 / 수정 / 교체)
- 남은 의문:
- 걸린 시간, 사용량:
```

## S1. Claude Code 구조화 실행 기본기

- 갈래: ① 실행 계층(후보 A2의 기반)
- 가설
  - H1 `claude -p --input-format stream-json --output-format stream-json`으로 한 프로세스에 여러 사용자 턴을 순서대로 넣을 수 있고, 턴 사이에 프로세스가 살아 있다.
  - H2 턴이 도는 중에 넣은 사용자 메시지는 버려지지 않고 줄을 선다(또는 끼어든다). 어느 쪽인지 확인한다. 중단(interrupt) 수단이 있다.
  - H3 `--session-id <uuid>`로 정한 id가 `system/init`·`result`의 `session_id`와 같고, 프로세스를 죽인 뒤 `--resume <uuid>`로 띄우면 같은 id·같은 기록으로 이어진다(새 id가 생기지 않는다).
  - H4 봇 정의를 넣는 플래그가 동작한다: `--append-system-prompt-file`(또는 `--system-prompt-file`), `--plugin-dir`(스킬), `--settings`(권한 규칙), `--mcp-config --strict-mcp-config`, `--model`, `--add-dir`(다른 레포 워크트리). 사용자 전역 스킬·설정이 섞이지 않게 막는 방법이 있다.
  - H5 `result` 이벤트에 턴별 사용량(토큰, `total_cost_usd`, 걸린 시간)이 나온다. 구독 로그인에서도 나오는지 확인한다(예산 단위 Q16의 근거).
- 방법: 스파이크 폴더에 레포 워크트리 둘(아무 빈 레포)을 두고, 작은 하네스 스크립트(언어 자유, 짧게)로 프로세스를 띄워 JSON 줄을 주고받는다. 각 가설마다 명령과 출력 발췌를 남긴다.
- 통과 기준: H1·H3·H4는 반드시 통과. H2는 동작 방식이 문서화되면 통과(어느 쪽이든 설계로 받는다). H5는 필드가 있으면 통과, 없으면 예산 단위를 다시 정한다.
- 실패 시 영향: H1 실패면 턴마다 프로세스를 새로 띄우는 방식(`-p` 1회 + `--resume`)으로 바꾼다. H3 실패면 R4 설계를 다시 한다(인스턴스 id 매핑은 그대로, 세션 id 갱신을 일지에 기록).
- 예상 시간: 4시간. 독립.

## S2. 권한 정책 무인 실행

- 갈래: ① 실행 계층(R3)
- 가설
  - H1 `--settings`의 allow/deny 규칙 + `--permission-mode`(`acceptEdits` 등)로 정한 범위 안에서는 어떤 승인 창도 없이 일한다.
  - H2 규칙 밖 요청은 `--permission-prompt-tool mcp__<서버>__<도구>`로 지정한 MCP 도구에 RPC로 오고, 그 도구의 allow/deny 응답이 그대로 반영된다. RPC가 오지 않는 경로가 없다(조용히 멈추지 않는다).
  - H3 오늘 멈췄던 경우가 모두 RPC 또는 거부로 나온다: (a) 허용 목록 밖 Bash, (b) 카드 폴더·`--add-dir` 밖 경로 쓰기, (c) 다른 git 루트로의 이동·작업(오늘의 "permission-root relocation" 창), (d) 웹 접근, (e) `AskUserQuestion` 같은 질문 도구.
  - H4 RPC에 답하지 않으면(도구가 시간 초과) 에이전트가 무한정 기다리지 않거나, 기다린다면 서버가 시간 초과 후 거부를 돌려줄 수 있다.
- 방법: 몇 줄짜리 stdio MCP 서버(요청을 파일에 적고 정해진 답을 돌려줌)를 만들고, (a)~(e)를 일으키는 프롬프트를 하나씩 넣는다. 각 경우의 이벤트 흐름(`permission_denied`, `result.permission_denials` 등)을 기록한다.
- 통과 기준: H1·H2 통과, H3의 (a)~(e) 전부가 RPC 또는 즉시 거부로 관측됨(조용한 멈춤 0건), H4에서 멈춤 상한을 서버가 정할 수 있음.
- 실패 시 영향: 조용히 멈추는 경로가 하나라도 있으면 그 경로를 정책에서 원천 차단(deny)하거나, 감시 타이머(출력 없음 N분 → "막힘" 이벤트)를 보조로 둔다.
- 예상 시간: 3시간. 독립.

## S3. 메시지 도구와 오케스트레이터 깨우기

- 갈래: ① 실행 계층 + ② 서버 코어(R2, Q5)
- 가설
  - H1 워커 인스턴스가 지침만으로 jadecode MCP 도구(`report`·`ask`·`propose`·`error`)를 알맞은 때에 부른다. 끝날 때 `report` 없이 끝나는 비율을 잰다.
  - H2 한가한 오케스트레이터 인스턴스(구조화 실행)에 "다이제스트 사용자 턴"(이벤트 몇 건을 seq와 함께 요약한 글)을 넣으면, 오케스트레이터가 seq를 확인 기록하고 알맞은 도구를 부른다(예: 워커 질문에 답하거나 사람에게 올림).
  - H3 오케스트레이터가 일하는 중에 들어온 이벤트는 쌓였다가 턴이 끝난 뒤 한 번에 들어가고, 손실이 없다(seq 빈틈 0).
  - H4 이벤트 발생 → 오케스트레이터 턴 시작까지 2초 안쪽(한가할 때).
- 방법: 메모리 큐 + 파일 일지만 있는 장난감 서버(언어 자유)와 MCP 도구, 오케스트레이터 1 + 워커 2. 시나리오 셋: (1) 워커가 질문 → 오케스트레이터가 답, (2) 워커가 "사람 절차" 해당 요청(보호 브랜치 병합) → 오케스트레이터가 사람에게 올림, (3) 워커 둘이 동시에 보고.
- 통과 기준: H2·H3 통과(시나리오 셋에서 올바른 행동, seq 빈틈 0), H4 충족, H1의 `report` 누락률을 숫자로 냄(누락이면 턴 종료 자동 기록으로 보완하는 설계는 이미 있음).
- 예상 시간: 4시간. 독립(S1과 같은 플래그를 쓰지만 각자 확인).

## S4. 사람 붙기 왕복 (구조화 ↔ TUI)

- 갈래: ① 실행 계층 + ④ UI(R4, X2)
- 가설
  - H1 구조화 실행으로 몇 턴 진행한 세션을 멈추고, PTY에서 `claude --resume <session_id>`로 대화형 TUI를 띄우면 앞 턴이 모두 보이고 같은 세션 id다.
  - H2 TUI에서 사람이 몇 턴 대화한 뒤 끝내고, 다시 구조화 실행으로 `--resume`하면 사람 턴까지 이어지고 id가 그대로다.
  - H3 같은 세션을 두 프로세스가 동시에 열면 무슨 일이 나는지 확인하고, 서버가 막을 수 있는 잠금 방법을 정한다(서버 쪽 잠금이면 충분한지).
  - H4 TUI 동안 상태를 잃지 않는다: `--settings`로 넣은 http 훅(`UserPromptSubmit`·`Notification`·`Stop`)이 서버 스텁에 상태를 보낸다.
- 방법: S1과 같은 하네스 + `script`/작은 PTY 래퍼. 화면은 아무 터미널에서 봐도 된다(GUI 렌더는 S6·S7 몫).
- 통과 기준: H1·H2 통과, H3에서 안전한 잠금 규칙 확정, H4에서 상태 이벤트 수신.
- 실패 시 영향: 왕복이 안 되면 "인스턴스에 붙기"는 첫 버전에서 대화 화면만 두고, 진짜 TUI는 별도 인스턴스(같은 카드에 사람 전용 인스턴스)로 띄우는 방식으로 바꾼다. → X2 질문에 반영.
- 예상 시간: 3시간. 독립.

## S5. 이벤트 일지·구독·재구성

- 갈래: ② 서버 코어(후보 B2)
- 가설
  - H1 서버가 이벤트마다 전역 seq를 매겨 카드별 `events.jsonl`에 쓰고(fsync 정책 포함) 색인 SQLite(WAL)에 넣는 쓰기 경로가, 쓰기 도중 `kill -9`에도 일지와 색인 사이에 복구 불가능한 어긋남을 남기지 않는다(재시작 때 일지 기준으로 색인을 맞춘다).
  - H2 색인을 지우고 일지 + `task.md`만으로 재구성하는 시간이 카드 1,000개·이벤트 10만 건에서 5초 안쪽(Mac 기준, Linux 서버에서도 잼).
  - H3 WebSocket JSON-RPC `events.subscribe{topics: ["project/p1/"], from_seq}`가 앞부분 일치로 거르고, 일부러 느리게 읽는 구독자도 끊기지 않고 따라잡는다(색인에서 읽어 보내므로).
  - H4 `task.md` 파일 감시(macOS FSEvents, Linux inotify)가 에이전트의 편집을 놓치지 않고, 서버 자신의 쓰기와 구별된다.
- 방법: Rust로 최소 서버(`tokio`, `rusqlite` 또는 `sqlx`, `notify`, `tokio-tungstenite` 정도). 합성 부하 생성기.
- 통과 기준: H1(어긋남 0, 30회 반복), H2(5초), H3(손실 0, 끊김 0), H4(누락 0, 자기 쓰기 구별).
- 실패 시 영향: H2가 크게 넘으면 색인 스냅샷 파일을 주기적으로 남기는 방식을 더한다. H1이 안 되면 "일지가 정본, 색인은 늦게 따라감"을 더 엄격히 한다.
- 예상 시간: 1일. 독립. 서버 언어가 Rust로 정해지기 전이라도 이 스파이크는 Rust로 한다(Q1 결정의 근거가 된다).

## S6. GPUI Mac 화면 시제품

- 갈래: ④ UI(후보 D1)
- 가설
  - H1 GPUI + gpui-kit으로 Mac 첫 화면의 뼈대 셋을 하루 안쪽에 만든다: 칸반(열 = 단계, 카드에 배지), 카드 상세(markdown `task.md` 렌더 — 표·코드 블록 포함 — + 메시지 이력 목록), diff 보기.
  - H2 터미널 보기: `alacritty_terminal`(Zed `terminal_view` 참고 또는 `gpui-terminal`)로 PTY 바이트 흐름을 그려 Claude Code TUI가 색·커서·줄바꿈까지 바르게 보인다.
  - H3 한국어 입력: 대화 입력창과 터미널에서 IME 조합(예: "한글 입력 시험")이 바르게 된다.
  - H4 웹뷰 의존이 없다(`cargo tree`에 `wry`·`webkit` 계열 없음).
- 방법: 가짜 데이터(JSON 파일)로 화면을 띄운다. 터미널은 로컬 PTY로 `claude`를 직접 띄운다. 스크린샷을 결과에 남긴다.
- 통과 기준: H1·H2·H4 통과. H3 실패는 기록하고 우회 방법(입력창만 네이티브 텍스트 필드) 가능성을 적는다.
- 예상 시간: 1~1.5일. 독립. Mac에서 돌아야 한다(서버 머신이 Mac이 아니면 Mac 세션에서 띄운다).

## S7. nsh 화면 시제품 (Mac + Android)

- 갈래: ④ UI(후보 D2)
- 가설
  - H1 nsh(Rust만, TSX 안 씀)로 S6의 H1과 같은 화면 셋을 만든다.
  - H2 nsh 내장 `Terminal`에 WebSocket 바이트 흐름을 이어 Claude Code TUI가 바르게 보인다(Mac, Android 에뮬레이터 둘 다).
  - H3 같은 화면 코드가 Android 에뮬레이터에서 큰 수정 없이 돈다(고친 줄 수를 잰다).
  - H4 한국어 IME(Mac, Android).
  - H5 웹뷰 의존이 없다.
- 방법: S6와 같은 가짜 데이터. 터미널 바이트는 Mac의 작은 PTY→WebSocket 중계기로 보낸다. nsh 버전·커밋을 기록한다.
- 통과 기준: H1·H2(Mac)·H5 통과면 "Mac 초안 후보로 가능", H3·H2(Android)까지 통과면 "4플랫폼 단일 경로로 가능".
- 예상 시간: 1~1.5일. 독립. Android SDK·에뮬레이터 준비 시간은 별도(브리프에 적기).

## S9. 평가 재실행(리플레이)

- 갈래: ③ 봇·자기개선(후보 C1의 핵심 위험)
- 가설
  - H1 끝난 카드의 시작 상태(레포별 시작 커밋, 시작 때의 `task.md`)를 이 워크스페이스의 기록(`arxiv/`, git 이력)에서 되살릴 수 있다. 되살리지 못하면 카드 시작 때 무엇을 기록해야 하는지 목록을 낸다.
  - H2 되살린 상태에서 봇 버전 둘(지침 한 문단만 다름)로 같은 카드를 다시 돌리고, 단계 종료 조건(명령 검사 + 리뷰 봇 판정)으로 채점할 수 있다.
  - H3 같은 버전을 두 번 돌린 점수 차이가 두 버전 사이 점수 차이보다 작다(판별력이 있다). 아니면 몇 번 돌려야 하는지 추정한다.
  - H4 카드 한 번 재실행의 시간·사용량을 잰다(K값·예산 단위 Q16의 근거).
- 방법: 이 워크스페이스에서 끝난 코드 카드 2개를 고른다(명령 검사가 있는 것이 좋다. 문서 카드만 있으면 작은 합성 카드 2개를 만든다). 재실행 상한 8회.
- 통과 기준: H1(되살림 가능 또는 기록 목록), H2(채점 자동화), H3·H4 숫자.
- 실패 시 영향: 판별력이 없으면 평가를 "재실행" 대신 "기록 기반 지표(첫 시도 통과, 리뷰 루프 횟수 등)의 이동 평균 비교 + 반영 후 되돌림"으로 바꾸는 안을 그릴링에 올린다.
- 예상 시간: 1일. 독립. 가장 비싼 스파이크.

## S8. herdr 재사용 반증 (2차, 선택)

- 갈래: ① 실행 계층(후보 A3)
- 목적: A3를 버리는 근거를 실측으로 확인한다. A2가 S1~S4에서 흔들릴 때만 돌린다.
- 가설: H1 herdr API로 `pane --cwd` + `agent start claude` + 상태 구독이 되고, 권한 창에서 2초 안에 `blocked`가 잡힌다. H2 herdr 서버 재시작 뒤 같은 Claude 세션으로 복구된다. H3 jadecode에 필요한 영구 이력·와일드카드를 herdr 밖에서 메우는 양을 추정한다.
- 규칙: `herdr integration install`을 쓰지 않는다(사용자 전역 Claude 설정을 바꿈). 필요한 훅은 `--settings`로 넣는다. 매니페스트 원격 자동 갱신을 끈다.
- 통과 기준: H1·H2 통과면 A3를 "실행 기층 후보"로 되살려 그릴링에 올린다. 아니면 차용 대상으로만 둔다.
- 예상 시간: 3시간. 독립.
