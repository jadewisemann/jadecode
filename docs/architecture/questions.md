## 구현 수단

### Q1. 서버를 무엇으로 만드는가

- 분류: 사용자
- 추천안: **새로 작성한다. 언어는 Rust.** herdr를 포크하거나 rex 위에 얹지 않는다. 대신 다음을 빌려 온다: herdr의 에이전트 상태 판독 매니페스트(`src/detect/manifests/*.toml`)와 live handoff 발상, rex의 Program Status Protocol(OSC 7501), 빈틈없는 seq + 스냅샷, JSON Schema 자기 서술 API, tailnet 리스너.
- 근거
  - jadecode의 핵심(프로젝트·카드·단계·경로·봇·메시지 이력·사람 절차)은 herdr에도 rex에도 없다. 포크해도 핵심은 새로 써야 하고, 얻는 것은 PTY 계층인데 추천 실행 계층(A2)은 PTY를 "터미널로 넘기기"에만 쓴다.
  - herdr: 약 29만 줄 단일 크레이트(라이브러리 타깃 없음), 1.0 전·반년 34회 릴리스, 외부 PR 자동 닫음, 이벤트 메모리 링 512개, 실행은 셸에 명령 타이핑.
  - rex: 소스·라이선스 공개 없음, 베타, 승인 API·이벤트 이력 없음.
  - Rust인 이유: 클라이언트 후보(GPUI·nsh)가 Rust라 프로토콜 타입·클라이언트 코어를 서버와 함께 쓴다. 단일 바이너리 배포(Mac → Linux). herdr 코드 조각과 ACP Rust 크레이트를 그대로 쓸 수 있다.
  - 대안: TypeScript(Bun/Node)는 Claude Agent SDK를 직접 쓰고 개발이 빠르지만, 클라이언트와 언어가 갈리고 SDK + 구독 로그인은 정책 회색 지대다(X1). Go는 MyGo가 모바일 탈락이라 이점이 적다.
- 묻는 이유: "포크 vs 직접 구현"과 언어는 취향이 갈리는 결정으로 사용자가 지목했다(2026-11-08).
- 물을 문장: "서버는 herdr 포크 없이 새로 쓰고, 언어는 클라이언트와 맞춰 Rust로 가려 합니다. 괜찮을까요? (대안: TypeScript — Agent SDK를 바로 쓰지만 클라이언트와 언어가 갈림)"
- 스파이크: S5(Rust로 서버 코어 시험), S8(선택: herdr 재사용 반증)

### Q2. 클라이언트 UI 수단

- 분류: 사용자
- 추천안: **Mac 초안은 GPUI + gpui-kit.** 프로토콜·캐시·구독은 UI와 무관한 Rust 클라이언트 코어로 떼어 둔다. Android 착수 직전에 nsh를 다시 평가하고, 그때도 미숙하면 플랫폼별 네이티브(SwiftUI + SwiftTerm, Compose + Termux view, 코어는 UniFFI)로 간다.
- 근거: GPUI는 Zed·Longbridge Pro로 Mac에서 검증됐고 gpui-kit에 markdown·diff·에디터가 있다. 모바일은 Android가 커뮤니티 0.1뿐, iPad는 실험적. nsh는 요구(네이티브 뷰, 모바일 터미널, markdown, diff, 웹뷰 없음)에 가장 잘 맞지만 첫 커밋 2026-10-14, v0.4.0이다. MyGo는 모바일이 없어 뺐다. 상세는 `candidates.md` ④.
- 묻는 이유: "검증된 수단으로 Mac부터, 모바일은 나중에 다시" vs "처음부터 4플랫폼 단일 코드베이스에 걸기"는 위험 선호가 갈리는 취향 문제다.
- 물을 문장: "Mac 초안은 GPUI로 만들고 모바일 수단은 Android 직전에 다시 정할까요, 아니면 처음부터 nsh 하나로 4플랫폼을 노릴까요? (S6·S7 결과를 같이 드립니다)"
- 스파이크: S6, S7

### Q3. 서버–클라이언트 API 형태와 오케스트레이터·인스턴스의 접근 방법

- 분류: 설계자
- 결정
  - JSON-RPC 2.0 over WebSocket. 로컬은 Unix 소켓(0600)과 루프백, 원격은 tailnet 리스너. 메서드는 `card.create`처럼 `대상.동사`.
  - 이벤트는 같은 연결로 푸시(`events.subscribe{topics, from_seq}`). 터미널 바이트는 일회용 티켓을 받은 별도 WebSocket.
  - 스키마는 서버 Rust 타입에서 JSON Schema로 뽑아 `api.schema`로 내준다. `server.version`에 판과 최소 판.
  - 에이전트 접근: 인스턴스마다 jadecode MCP 서버(stdio)를 `--mcp-config`로 붙인다. 인스턴스 토큰은 환경변수. 역할별 도구 목록(워커: `report`·`ask`·`propose`·`error`·카드 읽기, 오케스트레이터: 더해서 카드·경로·인스턴스·봇 조작). 사람·스크립트용 `jadecode` CLI는 같은 메서드를 감싼다. 스킬은 사용법 안내일 뿐 접근 수단이 아니다.
- 근거: 요청·응답과 푸시를 한 연결에서, 에이전트·스크립트가 읽기 쉬운 JSON, 스키마 자기 서술(rex 방식). MCP 도구 호출은 구조화된 메시지라 R2(보고 도구 없음)를 직접 푼다. 비교는 `candidates.md` ④ 프로토콜 표.
- 확인 스파이크: S1(H4 `--mcp-config`), S3

### Q4. 첫 버전에서 지원할 에이전트 종류

- 분류: 설계자
- 결정: **Claude Code 하나.** 공식 `claude` 바이너리를 구조화 실행(`-p` stream-json)으로 구동한다. 서버 안의 드라이버 인터페이스는 ACP 개념(new_session·load·prompt·cancel·update·request_permission)에 맞춰, 2순위 Codex(`codex app-server`)와 Gemini·opencode(ACP)를 드라이버만 더해 붙일 수 있게 한다. 봇 정의의 "에이전트 종류·모델" 칸은 `agent = "claude-code"`, `model`, `cli_version`.
- 근거: 지금 운영이 Claude Code다. 비대화 권한 RPC(`--permission-prompt-tool`)·훅·세션 id 지정이 가장 풍부하다. 첫 버전 범위를 줄인다.
- 뒤집힐 조건: 사용자가 첫 버전에 다른 에이전트를 꼭 원하면 S11을 1차로 올린다.
- 확인 스파이크: S1, (S11)

## 오케스트레이터와 메시지

### Q5. 오케스트레이터가 받는 신호

- 분류: 설계자
- 결정: 오케스트레이터는 담당 프로젝트 전체를 구독하고, 그중 아래 **깨우는 이벤트**가 오면 서버가 모아서 다이제스트 사용자 턴으로 넣는다(일하는 중이면 턴이 끝난 뒤 한 번에).
  1. 오케스트레이터에게 온 메시지: 워커의 보고·질문·제안·오류, 사람의 말
  2. 인스턴스 상태: 막힘(권한 RPC 대기), 종료(정상·실패·예산 소진)
  3. 단계 종료 조건 판정 결과(충족·실패)
  4. 사람 절차 처리 결과(승인·거절)
  5. 개선 고리 신호: 카드 K개 끝남, 한가함
  6. 예산 경고(봇별·총량의 80%, 100%)
  - 깨우지 않는 것: 파일 변경, 배지 변화, 다른 인스턴스의 도구 호출 같은 잡음. 다음 다이제스트에 개수만 붙인다.
- 근거: 그릴링 Q6가 미답이라 SPEC의 오케스트레이터 일(대화, 카드 발행·경로, 인스턴스 호출·판단, 메시지 수신, 개선 고리)에서 거꾸로 뽑았다. 다이제스트에 seq를 붙이고 오케스트레이터가 확인 seq를 기록하므로 "받았는가"가 이력으로 남는다(`candidates.md` ② 「오케스트레이터 깨우기」).
- 확인 스파이크: S3

### Q6. 구독·발행의 범위

- 분류: 설계자
- 결정
  - 주제는 경로다: `global`, `project/<p>`, `project/<p>/card/<c>`, `instance/<i>`, `bot/<b>`. 구독은 앞부분 일치(`project/<p>/`는 그 프로젝트의 모든 카드 포함).
  - 기본 구독: 오케스트레이터 인스턴스 = 담당 프로젝트 전체(서버가 영구 보관, 인스턴스가 바뀌어도 유지). 워커 = 자기 카드(자기 카드로 온 메시지, 경로 변경). 사람(클라이언트) = 보고 있는 화면의 주제 + 알림 설정의 주제.
  - 클라이언트 구독은 연결 상태다. 끊기면 마지막 seq부터 다시 붙는다(`from_seq`). 서버는 구독자별 버퍼를 두지 않고 색인에서 읽어 보낸다.
- 근거: SPEC "오케스트레이터는 자기 프로젝트의 카드·인스턴스 변화를 구독한다", "늦게 봐도 빠짐없이"(Q22). 카드·인스턴스 단위 구독은 앞부분 일치로 함께 해결된다.
- 확인 스파이크: S5

### Q7. 메시지는 누구에게 가는가

- 분류: 설계자
- 결정
  - 워커가 보내는 메시지의 기본 수신자는 담당 오케스트레이터다. 오케스트레이터가 답하거나, 사람 절차에 해당하거나 판단할 수 없으면 사람에게 올린다(`escalated_from` 칸에 원 메시지).
  - 예외: 인스턴스 막힘(권한 RPC 대기)은 오케스트레이터와 사람에게 동시에 알린다. SPEC이 "그래도 멈추면 사람에게 알린다"고 하므로.
  - 사람은 모든 메시지를 이력에서 보고 직접 답할 수도 있다(같은 API). 직접 답한 것은 오케스트레이터 다이제스트에 들어간다.
  - 메시지 칸: `kind`(report·question·proposal·error), `from`, `to`(orchestrator·human·instance), `card`, `reply_to`, `escalated_from`.
- 근거: 기본 창구는 오케스트레이터(Q23·Q31). 사람 개입 횟수가 개선 지표(Q17·Q27)이므로 경로가 분명해야 센다.
- 확인 스파이크: S3

### Q8. 오케스트레이터 하나가 여러 프로젝트를 맡을 때 인스턴스

- 분류: 설계자
- 결정: **(오케스트레이터 봇, 프로젝트) 쌍마다 인스턴스 하나.** 봇 정의(지침·스킬·봇 기억)는 전역으로 공유하고, 프로젝트 기억은 프로젝트 폴더에 둔다. 프로젝트마다 "오케스트레이터 자리"가 안정 id를 갖고, 그 아래 인스턴스는 세대가 바뀐다(맥락이 차거나 하루가 지나면 핸드오프 노트를 쓰고 새 세대로).
- 근거: 프로젝트 맥락이 섞이지 않는다. 한 프로젝트의 긴 판단이 다른 프로젝트의 반응을 막지 않는다. "경우에 따라 프로젝트 전용처럼 기능"(Q24)이 자연스럽다. 세션은 장기 맥락을 갖지 않는다(Q3·Q5)는 원칙을 오케스트레이터에도 적용한다.

## 카드와 단계

### Q9. 새 프로젝트의 기본 단계 목록

- 분류: 사용자
- 추천안: `시작 → 구체화 → 구현 → 리뷰 → PR → 완료`

  | 단계 | 목표 | 기본 종료 조건 |
  |---|---|---|
  | 시작 | 발행됨 | 오케스트레이터가 경로를 정함(봇 판정) |
  | 구체화 | `task.md`의 목표·범위·완료 조건을 채움 | 오케스트레이터 판정 |
  | 구현 | 변경 | 명령 검사(빌드·테스트) |
  | 리뷰 | 리뷰 봇 피드백 루프 | 리뷰 봇 통과 판정 |
  | PR | Draft PR | PR 열림 + 명령 검사(CI) |
  | 완료 | 병합 또는 닫힘 | 사람 절차(보호 브랜치 병합) 또는 닫힘 |

  옛 초안과 다른 점: '검증'은 구현의 명령 검사와 리뷰 단계로 나눴다. '보고'는 메시지(report)가 대신하므로 단계에서 뺐다. 문서·조사 카드는 경로에서 구현·PR을 건너뛴다.
- 묻는 이유: 보드 열이 곧 단계라 매일 보는 화면의 모양이 정해진다. 일하는 방식의 취향이다.
- 물을 문장: "기본 단계를 위 여섯으로 할까요? 옛 초안의 '검증'·'보고'를 뺀 것이 괜찮은지도 봐 주세요."

### Q10. 카드 사이의 선후행

- 분류: 설계자
- 결정: 시스템이 표현한다. `task.md` 앞머리 `depends_on: [<카드 id>]`. 서버는 보드에 선행 표시를 하고, 선행 카드가 완료되면 후행 카드 주제로 이벤트를 내 오케스트레이터를 깨운다. 시작을 막지는 않는다(언제 시작할지는 오케스트레이터 판단). 순환은 서버가 거절한다.
- 근거: 표현은 싸고 보드·신호에 바로 쓰인다. 강제는 오케스트레이터 판단(Q5·Q21)과 겹치고 유연성을 잃는다.

### Q11. 선행 카드 위에 이어서 할 때 브랜치

- 분류: 사용자
- 추천안: 기본은 **선행이 병합된 뒤 기본 브랜치에서 시작**한다. 선행이 사람 절차(병합 승인) 대기로 오래 막혀 있을 때만 오케스트레이터가 stacked(선행 브랜치 위)를 고를 수 있고, 카드 앞머리 `repos[].base`에 기록한다. 선행 병합 뒤 기준을 옮기는 일(리베이스 등)을 봇이 스스로 할지는 사람 절차 후보로 둔다.
- 묻는 이유: 사람의 병합 대기와 흐름 속도 사이의 취향이다. 이 워크스페이스의 사용자 지침은 "브랜치 이력 모양(병합·리베이스)은 사람이 정한다"이므로, 봇 자율 리베이스는 지금 규칙과 어긋날 수 있다.
- 물을 문장: "선행 카드가 병합 대기일 때 후행 카드를 그 브랜치 위에 쌓아도 될까요? 쌓는다면 병합 뒤 리베이스를 봇이 해도 되나요, 사람 절차로 둘까요?"

### Q12. `task.md` 형식과 카드 id·폴더 이름

- 분류: 설계자
- 결정
  - 앞머리 YAML의 `jadecode:` 묶음(서버만 씀)과 본문(누구나 씀)으로 나눈다.

    ```yaml
    ---
    jadecode:
      id: 01JC8Q...            # ULID, 바뀌지 않음
      project: jadecode
      title: architecture
      created: 2026-11-08
      repos:
        - { repo: jadecode, branch: docs/architecture, base: docs/spec-rewrite }
      path: [구체화, 리뷰]      # 거칠 단계
      stage: 구체화
      status: working          # 배지
      depends_on: []
    ---
    ```
  - 본문은 지금 agent-harness 양식을 잇는다: 목표·범위·하지 않을 일·완료 조건·결정 사항·다음 행동·마무리.
  - 폴더 이름은 지금 규칙 `MMDD-slug`. 같은 프로젝트 안에서 겹치면 `-2`를 붙인다. 정체성은 폴더 이름이 아니라 ULID다(이름을 바꿔도 이력이 이어진다).
  - 앞머리의 `jadecode:` 묶음을 서버 밖에서 바꾸면 서버가 그것을 API 호출로 보고 검사한다(`candidates.md` ② B2).
- 근거: 사람·에이전트가 계속 읽고 쓰는 파일이라 본문은 자유, 상태 칸만 서버 소유. 지금 워크스페이스와 이어진다(Q36).

### Q13. 카드를 `arxiv/`로 옮기는 시점과 주체

- 분류: 설계자
- 결정: 시점 = 마지막 단계 종료 조건 충족(PR 병합·닫힘 포함) + 그 카드의 인스턴스가 모두 끝남 + 기록 이양(Q20) 끝. 주체 = 오케스트레이터가 `card.archive`를 부르고 서버가 옮긴다(사람 절차 아님). 서버는 커밋 안 된 변경이 있는 워크트리가 있으면 거절한다. 카드 일지(`events.jsonl`)·`transcripts/`도 함께 간다. 위치는 `arxiv/<YYYY-MM>/<project>/<card>/`.
- 근거: 지금 `archive-work` 규칙(사용자 확인 뒤 보관)을 시스템 조건으로 바꿨다. 보관은 되돌릴 수 있는 정리라 사람 절차 기본값(Q30)에 없다.

### Q14. 사람 절차를 프로젝트별로 더하고 빼기, 그 화면

- 분류: 사용자
- 추천안: 사람만 더하고 뺄 수 있다. 오케스트레이터·자기개선은 바꾸지 못하고 바꾸자고 제안(proposal)만 한다. 기본값 다섯 가지를 빼는 것도 허용하되 서버가 한 번 더 확인한다. 정책 파일은 에이전트가 쓸 수 없는 `policy/projects/<p>.toml`에 둔다. 첫 버전 화면은 프로젝트 머리와 카드 상세에 읽기 전용 표시만 두고, 편집은 파일로 한다. 편집 화면은 Mac 첫 화면 다섯 가지 밖이므로 그다음.
- 묻는 이유: 안전 경계(무엇을 사람이 승인하나)를 사람이 바꿀 수 있게 할지, 그리고 첫 화면 범위에 영향을 준다.
- 물을 문장: "사람 절차는 사람만 바꾸고, 첫 버전은 파일 편집 + 화면 표시만 둘까요? 기본값(병합·배포·외부 메시지·예산 초과·프로젝트 삭제)을 빼는 것도 허용할까요?"

## 봇과 자기개선

### Q15. 봇 정의 폴더 형식과 버전 관리

- 분류: 설계자
- 결정
  - `bots/`는 git 레포 하나. `bots/<bot>/bot.toml`(agent·model·cli_version·역할 설명), `instructions.md`, `skills/<skill>/SKILL.md`, `memory/`.
  - 사람만 쓰는 값(권한 정책, 봇별 예산, 봇 수 상한, 예산 총량)은 `policy/`에 둔다. 서버는 개선 반영 커밋의 변경 경로가 `instructions.md`·`skills/`·`memory/` 안인지 검사한다.
  - 버전: 반영(`bot.publish`) 한 번 = 기본 가지의 커밋 하나(개선 카드의 여러 커밋은 반영 때 하나로 합침) + 태그 `<bot>/v<n>`. 되돌리기 단위 = 반영 하나(그 커밋의 revert). 인스턴스는 시작 때의 커밋 해시를 기록한다.
- 근거: 버전·되돌리기·차이 보기를 git이 이미 한다. 경계를 파일 경로로 강제한다(`candidates.md` ③ C1).
- 확인 스파이크: S1(H4: 봇 내용을 Claude Code에 넣는 플래그)

### Q16. K값, "한가할 때", 예산 단위

- 분류: 사용자
- 추천안
  - K와 한가함은 설계자 기본값으로 두고 설정에서 바꾼다: K = 5(봇별로 그 봇이 일한 카드 5개 완료마다), 한가함 = 프로젝트에 일하는 인스턴스가 0이고 15분 지남.
  - **예산 단위(사용자에게 묻는 부분)**: 토큰(입력·출력·캐시)을 기본 단위로 세고, 공식 단가로 환산한 금액을 함께 보인다. 인스턴스 실행 시간 상한을 보조로 둔다. 구독으로 돌리면 실제 청구액이 없으므로 금액은 "환산"이다.
- 묻는 이유: 예산은 사람이 정하는 한도(Q28)라 단위가 사람의 감각과 맞아야 한다. 과금 방식(X1)에 따라 의미가 달라진다.
- 물을 문장: "봇 예산을 토큰으로 세고 환산 금액을 같이 보여 드리면 될까요? 아니면 월 금액이나 시간으로 정하고 싶으신가요?"
- 스파이크: S1(H5 사용량 필드), S9(H4 카드 1회 재실행 비용)

### Q17. 평가 세트로 변경 전후를 견주는 방법

- 분류: 스파이크
- 설계 기본안
  - 카드가 시작될 때 "시작 스냅샷" 이벤트를 남긴다: 레포별 시작 커밋, 시작 때 `task.md` 내용 해시와 사본, 경로. 지금부터 남겨야 나중에 다시 돌릴 수 있다.
  - 재실행은 평가 전용 프로젝트 `_eval`의 일반 카드로 돈다: 시작 스냅샷에서 워크트리를 열고, 바꾼 봇 버전으로 같은 `task.md`를 일하게 한 뒤, 원래 카드의 단계 종료 조건(명령 검사·리뷰 봇 판정)과 지표(첫 시도 통과, 리뷰 루프 횟수)로 채점한다.
  - 판별력이 없으면(같은 버전 두 번의 차이가 버전 간 차이보다 큼) 재실행 대신 "기록 지표의 이동 평균 비교 + 반영 후 되돌림"으로 바꾸는 안을 그릴링에 올린다.
- 스파이크: S9

### Q18. 새 봇은 누가 만드는가

- 분류: 설계자
- 결정: 둘 다 만든다. 사람은 같은 API로 봇을 만든다(Q1 "사람도 같은 권한·API"). 오케스트레이터는 복제·분화로 만든다. "생겨나거나"는 오케스트레이터의 분화로 읽는다. 봇 수 상한(Q28)은 누가 만들었든 함께 센다. 오케스트레이터가 "제한한다"는 쓰지 않는 봇을 멈춤(retire) 상태로 돌리는 것이다(지우지 않음, 되돌릴 수 있음).
- 근거: Q1 원칙에서 바로 나온다. 원문 해석이라 아키텍처 그릴링에서 확인만 한다.

### Q19. 권한 정책의 내용과, 막혔을 때의 기본 처리

- 분류: 스파이크
- 설계 기본안
  - 권한 정책 = 도구·명령 allow/deny 목록, 쓰기 가능 경로(카드 폴더 + 그 카드의 워크트리), 네트워크 허용 목록, 사람 절차 명령 목록. 사람 절차 명령(보호 브랜치 병합, 배포 등)은 deny로 두고, 에이전트는 대신 `request_human_procedure` 도구를 부른다. `policy/`·`bots/`(개선 카드 밖) 쓰기는 deny.
  - 정책 밖 요청의 기본 처리: 권한 RPC → 인스턴스 "막힘" 배지 + 오케스트레이터 깨움 + 사람 알림(Q7). 정책은 사람이 정하므로 오케스트레이터는 정책 밖을 허용하지 못하고, 거부하며 다른 길을 안내하거나 사람에게 올린다. 사람은 "이번 한 번 허용" 또는 "정책에 추가"를 고른다. 30분 안에 답이 없으면 거부하고 `error` 메시지를 남긴다. 즉 "알림만"이 아니라 **거부가 기본이고 사람이 허용할 수 있다**.
- 스파이크로 확인할 것: 조용히 멈추는 경로가 정말 없는지, 다른 git 루트 이동 같은 신뢰 확인이 비대화 모드에서 어떻게 나오는지.
- 스파이크: S2

### Q20. 인스턴스의 생애

- 분류: 스파이크
- 설계 기본안
  - 상태: `starting → working ⇄ idle ⇄ blocked → ended(done | failed | stopped)`.
  - 끝나는 때: 오케스트레이터가 끝냄, 워커가 마지막 `report` 뒤 한가함 30분, 예산 소진, 카드 보관.
  - 끊김(프로세스 죽음·서버 재시작): 같은 jadecode 인스턴스 id로 `claude --resume <session_id>` 재시작, 세대 번호만 올리고 일지에 남긴다. 세션 id가 바뀌면 매핑만 갱신한다. 사람 붙기(터미널로 넘기기)도 같은 인스턴스의 세대다.
  - 기록 이양: `ended` 때 에이전트 기록(transcript)을 카드 `transcripts/<instance>.jsonl`로 복사하고 지표 이벤트를 남긴다. 봇이 실제로 흡수하는 것은 개선 카드에서다.
- 스파이크: S1(H3 resume 동일 id), S4(사람 붙기 왕복)

### Q21. 사람↔워커 직접 대화를 줄이도록 유도하는가

- 분류: 설계자
- 결정: 막지 않는다. 대신 (1) 직접 대화는 카드 이력에 `human_direct`로 남고 오케스트레이터 다이제스트에 들어가 맥락이 공유된다. (2) 지표 "사람 개입"에 세어 해당 워커 봇과 오케스트레이터의 개선 신호가 된다. (3) 붙기 화면에 "오케스트레이터에게 말하기"를 나란히 둔다.
- 근거: SPEC은 직접 대화를 허용하고 "많지 않아야" 한다고 했다(Q23). 사람 개입은 이미 개선 신호(Q17)다. 직접 대화가 잦다는 것은 오케스트레이터나 워커가 부족하다는 신호로 쓰는 것이 RSI 취지에 맞다.

## 저장과 배포

### Q22. 저장 위치, 프로젝트와 묶음 work는 같은가

- 분류: 설계자
- 결정: **프로젝트 = 묶음 work 폴더.** 레이아웃:

  ```
  <workspace>/
    repository/<repo>/                 # 원본 레포
    work/<project>/
      project.toml                     # 레포 목록, 단계 목록, 담당 오케스트레이터
      memory/                          # 프로젝트 기억
      events.jsonl                     # 프로젝트 일지(오케스트레이터 대화, 카드 생성 등)
      <MMDD-slug>/                     # 카드
        task.md                        # 앞머리 + 본문
        events.jsonl                   # 카드 일지(메시지·이벤트)
        handoff/  transcripts/
        <repo>/                        # 레포별 워크트리
    arxiv/<YYYY-MM>/<project>/<card>/  # 끝난 카드
    bots/                              # git 레포: 봇 정의와 버전
    policy/                            # 사람만: 권한·예산·상한, projects/<p>.toml(사람 절차)
    events/global.jsonl                # 전역 일지(봇 반영, 정책 변경, 인스턴스 생애)
    log/YYYY-MM-DD.md                  # 오케스트레이터 일일 기록
    .jadecode/                         # 지워도 되는 것: index.sqlite, 소켓, instances/<id>/ 실행 묶음
  ```

  지표는 일지에서 뽑아 색인에 둔다(재생성). 평가 결과는 개선 카드 일지와 `bots/` 반영 커밋 메시지에 남는다.
- 근거: Q3(파일 정본), Q22(이력), Q36(지금 구조 잇기). 지금 `work/jadecode/`가 이미 묶음 = 프로젝트처럼 쓰인다(오케스트레이터 줄, 하위 work).
- 확인 스파이크: S5

### Q23. 워크스페이스 기본 위치

- 분류: 설계자
- 결정: 첫 실행 때 사람이 고른다. `AGENT_WORKSPACE_ROOT`가 있으면 그것을, 없으면 `~/jadecode`를 제안한다. 고른 경로는 앱 설정(Mac `~/Library/Application Support/jadecode/config.toml`, Linux `~/.config/jadecode/config.toml`)에 둔다. 서버 하나는 워크스페이스 하나를 맡는다.
- 근거: 사소하고 되돌리기 쉽다. 지금 워크스페이스를 그대로 가리킬 수 있어야 한다(Q24).

### Q24. 지금 워크스페이스를 그대로 읽어 들이는가

- 분류: 사용자
- 추천안: 읽어 들인다. 옮기지 않고 제자리에서. 묶음 work → 프로젝트, 하위 work → 카드, 묶음 밖 단독 work → `기타` 프로젝트의 카드, `arxiv/` → 끝난 카드(평가 세트 후보). 단계는 추정하지 않고 '시작'에 두고 오케스트레이터가 분류한다. 허브의 세션 명단 표는 이력으로 옮기지 않고 본문에 남긴다.
- 묻는 이유: jadecode를 이 워크스페이스에서 만들며 써 보려면 필요하지만, 읽어 들이려면 기존 `task.md`에 앞머리를 써 넣어야 한다(파일 변경). agent-harness와 함께 쓰는 동안 둘이 같은 파일을 만지게 된다.
- 물을 문장: "지금 워크스페이스를 jadecode가 제자리에서 읽어 들이게 할까요? 그러려면 기존 `task.md` 맨 위에 앞머리를 써 넣어야 하는데, 괜찮을까요? (대안: 앞머리 대신 옆에 `.card.toml`을 따로 둠)"

### Q25. 원격 접속 방식, 에이전트를 다른 머신에서 돌리기

- 분류: 사용자
- 추천안: 원격 클라이언트 접속은 **Tailscale 하나**로 확정한다(시스템 `tailscaled` 위 리스너 + LocalAPI 신원 확인, `candidates.md` ⑤ E1). 에이전트는 **서버 머신에서만** 돈다. 다른 머신에서 돌리고 싶으면 그 머신에 서버를 하나 더 둔다(서버 간 연동은 비목표).
- 묻는 이유: "다른 머신에서 에이전트 실행"은 요구사항이다. 받아들이면 카드 폴더(정본 파일)가 머신 사이에 갈라져 동기화 장치가 필요해진다.
- 물을 문장: "원격은 Tailscale로만 붙고, 에이전트는 서버 머신에서만 돌게 해도 될까요?"
- 스파이크: (S10, Android 단계 전)

### Q26. 다중 사용자·로그인

- 분류: 설계자
- 결정: 한 사람. 로그인 없음. 인증 = 같은 OS 사용자(소켓 권한) + 원격 기기 토큰(짝짓기) + Tailscale 신원. 메시지·이벤트에는 처음부터 행위자 칸(`actor`: `human:<기기>` 또는 `instance:<id>`)을 둔다. 나중에 사람이 늘어도 이력 형식을 바꾸지 않게.
- 근거: 그릴링 전체가 사람 한 명을 전제로 했다. SPEC 개정 때 전제로 적기를 제안한다.

### Q27. 설치·배포·업데이트 방식

- 분류: 설계자
- 결정: Mac은 클라이언트 `.app` 안에 서버 바이너리를 넣고 LaunchAgent(launchd 사용자 서비스)로 띄운다. 앱을 닫아도 서버·인스턴스는 돈다. 첫 배포는 직접 빌드 → Homebrew cask, 자동 업데이트(Sparkle)는 나중. Linux는 단일 바이너리 + systemd 사용자 유닛. 데이터 형식 판을 파일에 적고, 서버는 자기보다 새 판을 만나면 멈춘다. 서버 업그레이드는 모든 인스턴스가 한가할 때 하거나 인스턴스를 재시작(`--resume`)한다.
- 근거: `candidates.md` ⑤. 업그레이드 중 일하는 인스턴스 처리는 그릴링 과제로 남긴다(아래).

### Q28. 알림 설정의 단위와 푸시 시점

- 분류: 설계자
- 결정: 설정 단위 = 프로젝트 × 이벤트 종류 표. 종류: 사람에게 온 질문, 막힘, 사람 절차 대기, 오류, 보고, 예산 경고. 기본값은 앞의 셋만 켬. 첫 버전은 Mac 알림 센터(클라이언트가 띄우는 로컬 알림). 푸시(APNs·FCM, 또는 셀프호스팅 중계)는 Android 클라이언트 단계에서 넣는다.
- 근거: Q33(푸시 후순위). 기본값은 "사람이 움직여야 하는 것"만.

## 설계 중 나온 사용자 질문 (28개 밖)

### X1. Claude 과금: 구독 로그인 vs API 키

- 분류(추가): 사용자
- 사실: Claude Code 법적 고지(code.claude.com/docs/en/legal-and-compliance)는 구독 로그인을 Claude Code의 일반 사용에 허용하고, "수정하지 않은 Claude Code 바이너리에 본인 구독으로 로그인"하는 것을 막지 않는다. Agent SDK로 만든 제품에서 구독 로그인을 쓰는 것은 회색 지대다(미확인). 구독 한도는 "일반적인 개인 사용"을 전제로 한다.
- 추천안: 구독 + 공식 `claude` 바이너리를 구조화 실행으로 구동한다(그래서 실행 계층을 SDK가 아니라 CLI 구동으로 잡았다). 개선 고리·평가 재실행으로 사용량이 한도를 넘기 시작하면 그 부분만 API 키로 돌리는 선택지를 둔다.
- 물을 문장: "인스턴스는 지금처럼 본인 구독으로 공식 `claude`를 돌리고, 평가 재실행처럼 많이 쓰는 부분만 필요하면 API 키를 쓰는 방향이 괜찮을까요?"

### X2. "인스턴스에 직접 붙기"의 모양

- 분류(추가): 사용자
- 추천안: 기본은 구조화된 대화 화면(메시지·도구 호출·diff를 네이티브로 그림). "터미널로 넘기기"로 진짜 Claude Code TUI를 터미널 보기에 띄우는 것은 S4가 통과하면 첫 버전에 넣는다.
- 묻는 이유: SPEC Mac 첫 화면 5번 "인스턴스에 직접 붙기"가 진짜 터미널을 뜻하는지, 대화만 되면 되는지가 첫 버전 범위를 바꾼다.
- 물을 문장: "인스턴스에 붙을 때 대화 화면이면 충분한가요, 아니면 실제 Claude Code 터미널 화면이 꼭 필요한가요?"

## 아키텍처 그릴링으로 넘길 설계 과제

사용자에게 묻지 않고 그릴링에서 설계자끼리(또는 사용자 확인만) 정할 것들이다.

- 서버 업그레이드 때 일하는 인스턴스: 한가할 때까지 미룸 vs 인스턴스를 별도 감독 프로세스에 두기(herdr live handoff 참고).
- `task.md` 앞머리를 서버 밖에서 바꿨을 때의 정확한 규칙(받아들임·되돌림 경계).
- 오케스트레이터 세대 교체 기준(맥락 크기, 시간, 사람 요청).
- 예산 강제 방식: 다 쓰면 인스턴스를 멈추는가, 사람 절차(예산 초과)로 승인을 기다리는가.
- 개선 반영 뒤 이미 일하는 인스턴스의 처리(SPEC은 영향 없음), 되돌리기 뒤 지표 비교 방식.
