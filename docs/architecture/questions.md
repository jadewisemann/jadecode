## 구현 수단

### Q1. 서버를 무엇으로 만드는가

- 분류: 사용자
- 상태: 확정(사용자 A1, 2026-11-09 "좋음")
- 결정: **새로 작성한다. 언어는 Rust.** herdr를 포크하거나 rex 위에 얹지 않는다. 빌려 오는 것: herdr의 상태 판독 매니페스트와 live handoff 발상, rex의 Program Status Protocol·빈틈없는 seq + 스냅샷·JSON Schema 자기 서술 API·tailnet 리스너.
- 근거: jadecode의 핵심(카드·단계·봇·메시지 이력·사람 절차)은 herdr에도 rex에도 없다. herdr는 약 29만 줄 단일 크레이트·이벤트 메모리 링 512개, rex는 소스 비공개·승인 API 없음. Rust는 클라이언트(GPUI)와 프로토콜 타입·클라이언트 코어를 함께 쓴다.
- 스파이크 뒤: S5 시제품(Rust 약 2,100줄, tokio·rusqlite·notify·tokio-tungstenite)이 서버 코어를 Rust로 세울 수 있음을 보였다. A2가 흔들리지 않아 S8(herdr 반증)은 필요 없다. berth(Go)의 데몬 로직은 Rust로 옮기는 쪽을 추천한다(라운드 B3).

### Q2. 클라이언트 UI 수단

- 분류: 사용자
- 상태: 확정(사용자 A2)
- 결정: **Mac은 GPUI(+ gpui-kit)로 시작한다.** nsh는 Android 단계에서 재평가한다. 프로토콜·캐시·구독은 UI와 무관한 Rust 클라이언트 코어로 떼어 둔다.
- 스파이크 뒤: S6·S7은 돌리지 않았다. Mac 화면 다섯 가지, 터미널 렌더, 한국어 IME는 Mac 클라이언트 첫 카드에서 [구현 중 확인](2026-11-09 사용자 결정). berth 데스크톱(GPUI, `alacritty_terminal` 터미널 격자 + IME 입력창 + 대화 화면)을 출발점으로 쓰면 이 위험이 준다(라운드 B3).

### Q3. 서버–클라이언트 API 형태와 오케스트레이터·인스턴스의 접근 방법

- 분류: 설계자
- 상태: 확정(설계자, S1·S3)
- 결정
  - JSON-RPC 2.0 over WebSocket. 로컬은 Unix 소켓(0600)과 루프백, 원격은 tailnet 리스너. 메서드는 `card.create`처럼 `대상.동사`.
  - 이벤트는 같은 연결로 푸시(`events.subscribe{topics, from_seq}`). 터미널 바이트는 일회용 티켓을 받은 별도 WebSocket.
  - 스키마는 서버 Rust 타입에서 JSON Schema로 뽑아 `api.schema`로 내준다. `server.version`에 판과 최소 판.
  - 에이전트 접근: 인스턴스마다 jadecode MCP 서버(stdio)를 `--mcp-config --strict-mcp-config`로 붙인다. 인스턴스 토큰은 환경변수. 역할별 도구 목록(워커: `report`·`ask`·`propose`·`error`·`read_card`, 오케스트레이터: `ack`·`reply`·`escalate`·`send`와 카드·경로·인스턴스·봇 조작). 사람·스크립트용 `jadecode` CLI는 같은 메서드를 감싼다.
- 스파이크 근거: MCP 연결·토큰 환경변수 전달이 동작했다(S1 H4). 워커가 도구 설명만으로 알맞은 때에 불렀다(완료 카드 26/26 `report(done)`, S3 H1). MCP 도구는 지연 로딩(`ToolSearch`)되지만 지침에 이름을 적으면 바로 찾는다(S1). S5 시제품이 WebSocket JSON-RPC 구독을 이 모양으로 구현했다.

## 오케스트레이터와 메시지

### Q5. 오케스트레이터가 받는 신호

- 분류: 설계자
- 상태: 확정(설계자, S3)
- 결정: 오케스트레이터는 담당 프로젝트 전체를 구독하고, 아래 **깨우는 이벤트**가 오면 서버가 모아서(0.3초, 설정값) 다이제스트 사용자 턴으로 넣는다. 일하는 중이면 턴이 끝난 뒤 한 번에 넣는다. 다이제스트에는 seq를 붙이고 오케스트레이터는 마지막 seq를 `ack`한다.
  1. 오케스트레이터에게 온 메시지: 워커의 보고·질문·제안·오류, 사람의 말
  2. 인스턴스 상태: 막힘(권한 RPC 대기), 종료(정상·실패·예산 소진), `report(done)` 없이 한가함으로 넘어감
  3. 단계 종료 조건 판정 결과(충족·실패)
  4. 사람 절차 처리 결과(승인·거절)
  5. 개선 고리 신호: 봇별 카드 K개 끝남, 한가함, 반영 뒤 지표 악화(자동 되돌림)
  6. 예산 경고(봇별·총량의 80%, 100%), 계정 이용률 임계(라운드 B6)
  - 깨우지 않는 것: 파일 변경, 배지 변화, 다른 인스턴스의 도구 호출, **턴 종료 자동 기록(`report(auto)`)**, 직전에 "기다려라"를 받은 인스턴스의 무도구 턴. 다음 다이제스트에 개수만 붙인다.
  - 재전달: 오케스트레이터 인스턴스가 바뀌면 마지막 ack 뒤의 이벤트를 다시 넣고 "마지막 ack 이후 이 자리의 오케스트레이터가 한 행동" 목록을 앞에 붙인다(at-least-once + 중복 행동 방지).
- 스파이크 근거: 다이제스트 58개 전부 정확히 ack, 깨우는 이벤트 130건 빠짐·중복 0, 한가할 때 서버·CLI 지연 0.3초 남짓(모델 첫 응답 중앙값 2.06초는 서버로 줄일 수 없음), 자동 기록이 헛 깨우기 7건을 만든 것, ack 전 죽음 → 재전달에서 중복 행동 0(S3).
- [구현 중 확인]: 몇 시간·수백 다이제스트 뒤 자동 압축이 ack 규칙을 지키는지, 오케스트레이터 기본 모델.

### Q6. 구독·발행의 범위

- 분류: 설계자
- 상태: 확정(설계자, S5)
- 결정
  - 주제는 경로다: `global`, `project/<p>`, `project/<p>/card/<c>`, `instance/<i>`, `bot/<b>`. 구독은 **경로 마디 단위** 앞부분 일치(`project/p1/`은 그 프로젝트의 모든 카드, `project/p1`이 `project/p10`에 맞지 않음).
  - 기본 구독: 오케스트레이터 인스턴스 = 담당 프로젝트 전체(서버가 영구 보관, 인스턴스가 바뀌어도 유지). 워커 = 자기 카드. 사람(클라이언트) = 보고 있는 화면의 주제 + 알림 설정의 주제.
  - 클라이언트 구독은 연결 상태다. 끊기면 마지막 seq부터 다시 붙는다(`from_seq`). 서버는 구독자별 버퍼를 두지 않고 색인에서 읽어 보낸다.
- 스파이크 근거: 구독자 6종(느림·20~40초 멈춤·재접속·마디 경계 포함) × 부하 3가지에서 손실·중복·순서 어긋남·끊김 0, 멈춘 구독자가 있어도 서버 RSS 약 36MB 일정(S5 H3).

### Q7. 메시지는 누구에게 가는가

- 분류: 설계자
- 상태: 확정(설계자, S3)
- 결정
  - 워커 메시지의 기본 수신자는 담당 오케스트레이터다. 오케스트레이터가 답하거나, 사람 절차에 해당하거나 판단할 수 없으면 사람에게 올린다(`escalated_from`).
  - 예외: 인스턴스 막힘은 오케스트레이터와 사람에게 동시에 알린다.
  - 사람은 모든 메시지를 이력에서 보고 직접 답할 수 있다. 직접 답한 것은 오케스트레이터 다이제스트에 들어간다.
  - 메시지 칸: `kind`(report·question·proposal·error·instruction), `from`, `to`, `card`, `reply_to`, `escalated_from`, `actor`. 오케스트레이터 → 인스턴스 메시지도 `reply_to`를 받고, 사람 결정 전달은 원래 제안의 seq를 잇는다.
  - 워커의 AskUserQuestion은 권한 RPC에서 가로채 `question` 메시지로 바꾼다(S2).
- 스파이크 근거: 질문 → 답, 병합 제안 → 사람에게 올림 + 워커에 대기 지시, 사람 결정 → 워커 전달이 모두 올바르게 돌았고 오케스트레이터가 사람 절차를 스스로 승인한 경우 0. `send`가 실마리를 잃은 1건 → `reply_to` 규칙(S3).

### Q8. 오케스트레이터 하나가 여러 프로젝트를 맡을 때 인스턴스

- 분류: 설계자
- 상태: 확정(설계자)
- 결정: **(오케스트레이터 봇, 프로젝트) 쌍마다 인스턴스 하나.** 봇 정의는 전역으로 공유하고 프로젝트 기억은 프로젝트 폴더에 둔다. 프로젝트마다 "오케스트레이터 자리"가 안정 id를 갖고, 그 아래 인스턴스는 세대가 바뀐다(맥락이 차거나 하루가 지나면 핸드오프 노트를 쓰고 새 세대로). 세대가 바뀔 때 Q5의 재전달 규칙이 적용된다.
- 근거: 프로젝트 맥락이 섞이지 않고, 한 프로젝트의 긴 판단이 다른 프로젝트의 반응을 막지 않는다. 세션은 장기 맥락을 갖지 않는다(SPEC Q3·Q5).

### Q9. 새 프로젝트의 기본 단계 목록

- 분류: 사용자
- 상태: 확정(사용자 A3)
- 결정: `시작 → 구체화 → 구현 → 리뷰 → PR → 완료`

  | 단계 | 목표 | 기본 종료 조건 |
  |---|---|---|
  | 시작 | 발행됨 | 오케스트레이터가 경로를 정함(봇 판정) |
  | 구체화 | `task.md`의 목표·범위·완료 조건을 채움 | 오케스트레이터 판정 |
  | 구현 | 변경 | 명령 검사(빌드·테스트) |
  | 리뷰 | 리뷰 봇 피드백 루프 | 리뷰 봇 통과 판정(`--json-schema` 판정 JSON, S9) |
  | PR | Draft PR | PR 열림 + 명령 검사(CI) |
  | 완료 | 병합 또는 닫힘 | 사람 절차(보호 브랜치 병합) 또는 닫힘 |

- 스파이크 근거: 리뷰 봇 판정은 같은 결과물 두 번에 평균 0.12점 차·판정 불일치 0/8로 재현성이 높아 종료 조건으로 쓸 만하다(S9 H2).

### Q10. 카드 사이의 선후행

- 분류: 설계자
- 상태: 확정(설계자 + 사용자 A4 표기)
- 결정: 시스템이 표현한다. `task.md` 앞머리에 **대상 카드와 시점**을 함께 적는다(라운드 A4).

  ```yaml
  depends_on:
    - { card: 01JC8Q..., at: merged }        # 기본: 선행 카드 PR 병합(완료 단계)
    - { card: 01JC9R..., at: "리뷰:passed" } # 선행 카드의 리뷰 단계 종료 조건 충족
    - { card: 01JCAA..., at: "PR:entered" }  # 선행 카드가 PR 단계에 들어감
  ```

  - `at` 값: `merged`(기본, 생략 시), `done`(완료 단계 도달, 병합 없이 닫힌 경우 포함), `<단계>:entered`, `<단계>:passed`.
  - 서버는 보드에 선행 표시를 하고, 조건이 충족되면 후행 카드 주제로 이벤트를 내 오케스트레이터를 깨운다. 시작을 막지는 않는다(오케스트레이터 판단). 순환은 서버가 거절한다.
  - 조건 충족 시점은 시작 스냅샷(③)에 함께 남긴다(S9 목록 7).
- 근거: 표현은 싸고 보드·신호에 바로 쓰인다. 시점 표기로 "병합 전에 이어서 시작"도 같은 칸으로 표현된다(Q11).

### Q11. 선행 카드 위에 이어서 할 때 브랜치

- 분류: 사용자
- 상태: 일부 라운드 B7
- 결정(라운드 A4): 기본은 **선행 카드가 병합된 뒤 기본 브랜치에서 시작**한다. 선행 조건의 시점이 병합 전(`<단계>:entered`·`<단계>:passed`)이면 후행 카드는 선행 카드 브랜치 위에서 시작하고(stacked), 카드 앞머리 `repos[].base`에 그 브랜치와 시작 커밋을 적는다.
- 남은 것: 선행이 병합된 뒤 후행 브랜치의 기준을 기본 브랜치로 옮기는 일(리베이스 등)을 봇이 스스로 할지, 사람 절차로 둘지 → 라운드 B7.

### Q18. 새 봇은 누가 만드는가

- 분류: 설계자
- 상태: 확정(설계자)
- 결정: 둘 다 만든다. 사람은 같은 API로 봇을 만든다(SPEC Q1 "사람도 같은 권한·API"). 오케스트레이터는 복제·분화로 만든다. "생겨나거나"는 오케스트레이터의 분화로 읽는다. 봇 수 상한은 누가 만들었든 함께 센다. 오케스트레이터가 "제한한다"는 쓰지 않는 봇을 멈춤(retire) 상태로 돌리는 것이다(지우지 않음, 되돌릴 수 있음).

### Q19. 권한 정책의 내용과, 막혔을 때의 기본 처리

- 분류: 스파이크
- 상태: 닫힘(S2)
- 결정
  - 권한 정책 = 도구·명령 allow/deny 목록, 쓰기 가능 경로(카드 폴더 + 그 카드의 워크트리 = cwd + `--add-dir` + `acceptEdits`), 읽기 범위(다른 카드 폴더 deny, S3), 네트워크 허용 목록, 사람 절차 명령 목록, 허용 스킬 목록(나머지 내장 스킬 deny, S1), `attribution` 값(S1).
  - 막을 명령은 **settings `deny`** 로 둔다. allow 목록에서 빼는 것만으로는 부족하다(읽기 전용으로 판정되는 명령은 묻지 않고 실행됨). 사람 절차 명령(보호 브랜치 병합, 배포 등)·네트워크 명령은 deny이고, 에이전트는 대신 `request_human_procedure` 도구를 부른다. `policy/`·`bots/`(개선 카드 밖) 쓰기도 deny.
  - 정책 밖 요청: `--permission-prompt-tool mcp__jadecode__permission`으로 권한 RPC → 서버가 즉시 `instance.blocked`를 일지에 씀 + 오케스트레이터 깨움 + 사람 알림. 오케스트레이터는 정책 밖을 허용하지 못하고, 거부하며 다른 길을 안내(거부 `message`가 그대로 도구 결과가 됨)하거나 사람에게 올린다. 사람은 "이번 한 번 허용" 또는 "정책에 추가"(파일 편집, Q14)를 고른다.
  - 상한: **25분** 안에 답이 없으면 서버가 거부를 돌려준다. CLI는 MCP 도구 무응답 1800초에 스스로 끊는데 그것은 거부가 아니라 도구 오류라서, 처리기 상한 < 1800초를 계약 테스트로 지킨다.
  - 막힘·거부의 정본은 서버의 권한 RPC 기록이다. 권한 서버 장애(시간 초과·연결 끊김)는 도구 오류로, 권한 서버 시작 실패는 `result` 없는 rc=1로 나오므로, 시작 때 init `mcp_servers[]`의 연결 상태를 확인하고 아니면 인스턴스를 바로 `failed`로 둔다.
- 스파이크 근거: 오늘 멈췄던 다섯 경우(허용 밖 Bash·복합 명령·명령 치환, 카드 밖 쓰기, 다른 git 루트 `cd`·`git -C`, WebFetch·WebSearch, AskUserQuestion) 모두 RPC 또는 즉시 거부, 조용한 멈춤 0(S2 H3). 서버 상한 deny·interrupt·`MCP_TOOL_TIMEOUT` 모두 동작(S2 H4).

### Q20. 인스턴스의 생애

- 분류: 스파이크
- 상태: 닫힘(S1·S4)
- 결정
  - 상태: `starting → working ⇄ idle ⇄ blocked → ended(done | failed | stopped)`. 이와 따로 실행 임대 상태 `structured | handoff | terminal | idle`(S4 R-a). 인스턴스당 claude 프로세스는 최대 하나.
  - 시작: `--session-id <서버가 만든 uuid>`. 시작 직후 init에서 jadecode MCP 연결을 확인한다(S2).
  - 끝나는 때: 오케스트레이터가 끝냄, 워커가 마지막 `report(done)` 뒤 한가함 30분, 예산 소진, 카드 보관. 끝내는 방법은 stdin 닫기(한가할 때) 또는 SIGTERM → 5초 → SIGKILL, 비정상 종료 뒤 고아 도구 프로세스를 cgroup으로 치운다(S1).
  - 끊김(프로세스 죽음·서버 재시작): 같은 jadecode 인스턴스 id, **같은 카드 폴더**에서 `claude -p --resume <같은 uuid>`로 다시 띄우고 세대 번호만 올린다. "already in use"·"No conversation found"를 구별한다(S1 H3). 세션 id는 왕복·kill 뒤에도 바뀌지 않았다(S1, S4).
  - 사람 붙기: 첫 버전은 대화 화면(라운드 A10)이라 프로세스를 바꾸지 않는다. 터미널로 넘기기(2차)는 같은 인스턴스의 세대이고, 넘기기 순서·외부 감지·갈라짐 감지는 S4 R-b~R-d를 따른다.
  - 기록 이양: `ended` 때 전사(`~/.claude/projects/<cwd>/<uuid>.jsonl`)를 카드 `transcripts/<instance>.jsonl`로 복사하고 지표 이벤트를 남긴다. 봇이 흡수하는 것은 개선 카드에서다.
- [구현 중 확인]: 몇 시간 유휴·잠자기 뒤 같은 프로세스 생존(실패하면 `--resume`), TUI 안 `Esc` 중단의 훅 흐름.

    work/<project>/
      project.toml                     # 레포 목록, 단계 목록, 담당 오케스트레이터

## 라운드 B — 사용자에게 물을 것

라운드 A 답과 1차 스파이크 결과에서 새로 생긴, 취향이 갈리거나 요구사항에 영향을 주는 질문이다. 질문마다 추천안을 맨 앞에 둔다. 앞의 넷(B1~B4)은 오케스트레이터가 묻기로 한 주제이고, 뒤의 셋(B5~B7)은 이번 통합에서 더한 것이다.

### B1. RSI 평가 방식: 결과 점수 재실행 비교를 버리고 무엇으로 견주나 (S9)

- 배경: SPEC 자기개선 고리 3단계는 "평가 세트로 변경 전후를 견주고, 나아졌으면 새 버전으로 반영"이다. S9에서 결과 점수(수용 테스트·단계 통과·리뷰 점수) 재실행 비교는 판별력이 없었다. 같은 버전 안 흔들림이 버전 간 차이보다 컸고, 가르려면 버전당 약 17회가 필요하다고 추정됐다(실제 카드라면 한 고리에 수십~수백 회 실행). 반면 바꾼 지침이 겨냥한 행동을 세는 지표("더한 테스트 수")는 적은 횟수로 갈랐다.
- **추천안**: 고리 3단계를 셋으로 바꾼다.
  1. 개선 카드는 변경안과 함께 **겨냥한 행동 지표**(예: 테스트 추가 수, 커밋 누락률, 리뷰 루프 횟수)를 적고, 작은 평가 카드 몇 개의 재실행에서 그 지표가 나아졌는지 본다.
  2. 결과 점수는 "나빠지지 않았는가"의 **회귀 검사**로만 쓴다.
  3. 반영 뒤 같은 봇의 실제 카드 K개 기록 지표를 이전 버전과 견주고, 나빠지면 서버가 **자동으로 되돌린다**.
  - 사람 승인은 여전히 없다.
  - 지표는 사람이 `policy/`에 둔 **지표 목록에서만** 고른다. 개선 봇이 자기에게 유리한 지표를 새로 만들지 못하게 하기 위해서다.
- 대안
  - (나) 재실행 비교를 유지하고 횟수를 늘린다: 판별력은 생기지만 비용이 크고 구독 이용률을 크게 쓴다(B6).
  - (다) 재실행 없이 반영 후 관찰 + 자동 되돌림만 쓴다: 가장 싸지만 나쁜 변경이 실제 카드 K개 동안 쓰인다.
- 물을 문장: "봇 개선을 '결과 점수 재실행 비교' 대신 '겨냥한 행동 지표로 견주기 + 회귀 검사 + 반영 후 나빠지면 자동 되돌림'으로 바꿀까요? 견줄 지표 목록은 사람이 `policy/`에 정하는 걸로 할까요?"
- SPEC 영향: 「자기개선(RSI) 고리」 3단계 문장과 「신호」의 평가 세트 문장이 바뀐다.

### B2. 사람이 터미널로 붙어 있는 동안 워커는 멈춘다 (S4)

- 배경: 같은 세션을 두 프로세스가 동시에 열면 claude는 막지 않고 대화가 조용히 갈라지며, 다시 열면 한쪽 가지가 오류 없이 사라진다. 그래서 인스턴스당 프로세스를 하나로 제한해야 하고, 사람이 "터미널로 넘기기"로 진짜 TUI에 붙으면 그 동안 구조화 실행(오케스트레이터 지시를 받는 쪽)은 멈춘다. 첫 버전의 대화 화면(라운드 A10)은 같은 프로세스에 말을 넣으므로 멈추지 않는다.
- **추천안**
  - 첫 버전(대화 화면): 워커를 멈추지 않는다. 사람의 말은 오케스트레이터 메시지처럼 다음 도구 경계나 다음 턴에 들어간다. 급하면 "중단" 버튼(interrupt)으로 현재 턴을 끊는다.
  - 터미널로 넘기기(2차): 넘기는 동안 그 인스턴스의 구조화 실행은 멈춘다. 오케스트레이터 메시지는 큐에 쌓이고, 배지 "사람이 붙어 있음"을 보인다. 사람이 TUI를 닫으면 같은 세션으로 구조화 실행이 이어지고 쌓인 메시지가 들어간다.
  - 사람이 jadecode 밖 터미널에서 같은 세션을 열면 막지 못하고 감지만 한다("다른 곳에서 열림", 비공식 파일에 기대므로 확실하지 않음).
- 대안: 터미널로 넘기기 대신 같은 카드에 사람 전용 인스턴스를 따로 띄운다. 워커는 멈추지 않지만 사람과 워커의 맥락이 갈린다.
- 물을 문장: "나중에 '터미널로 붙기'를 넣으면 사람이 붙어 있는 동안 그 워커는 일을 멈추고 오케스트레이터 지시는 쌓아 둡니다. 괜찮을까요? (첫 버전 대화 화면에서는 멈추지 않습니다)"

### B3. berth와의 관계

- 배경: `repository/berth`(사용자 레포, 커밋 없음, 2026-10-28 작성)는 Go 데몬 + GPUI 데스크톱 + PWA로 "Claude Code 세션을 어느 기기에서나 실행·관찰·승인"한다. 데몬은 A2(stream-json 구동)와 터미널 넘기기(TUI 세션과 `resume`으로 서로 넘어감)를 작은 규모로 이미 구현했고, 데스크톱은 S6가 확인하려던 GPUI 터미널 격자(`alacritty_terminal`)·한국어 IME 입력창·대화 화면·승인 버튼을 갖고 있다. 반면 이벤트 이력은 메모리에만 있고, 카드·봇·메시지 이력이 없으며, 언어가 Go(서버는 Rust로 확정, A1)이고, 웹·Android는 PWA라 jadecode의 네이티브 원칙과 맞지 않는다. 상세는 `candidates.md` ① 「berth와의 관계」.
- **추천안**: (가) **jadecode가 berth를 흡수한다.**
  - berth 데스크톱의 터미널 보기·입력창·대화 화면 코드를 jadecode Mac 클라이언트의 출발점으로 가져온다.
  - 데몬의 드라이버 로직(stream-json 처리, TUI 스냅숏, 훅 설정)은 Rust로 옮겨 jadecode 서버 드라이버에 넣는다.
  - berth는 따로 키우지 않는다. dev 서버 노출(`berth run`)과 PWA는 jadecode 범위 밖이라 보류한다.
- 대안
  - (나) 둘 다 두고 jadecode 서버가 berth 데몬을 실행 기층으로 쓴다: 두 언어·두 데몬이 생기고, 이력이 berth 메모리와 jadecode 일지에 갈린다.
  - (다) 따로 두고 서로 참고만 한다: 같은 일을 두 번 한다.
- 물을 문장: "berth는 jadecode에 흡수할까요? 데스크톱 코드는 jadecode Mac 클라이언트의 출발점으로, 데몬 로직은 Rust 서버로 옮기고 berth는 따로 키우지 않는 방향입니다. 아니면 berth를 별도 제품(기기 어디서나 Claude Code 원격 조작 + dev 서버 노출)으로 계속 두실 건가요?"

### B4. 2차 스파이크를 돌릴지

- 배경: 1차 결과로 A2·B2·C1이 섰다. 2차 후보는 S8(herdr 반증), S10(Tailscale 리스너), S11(다른 벤더 드라이버)이다. S6·S7(화면)은 2026-11-09 결정대로 구현하면서 확인한다. 1차에서 새로 생긴 작은 확인거리로 "git 워크트리가 원본 레포의 폴더 신뢰를 물려받는가"가 있다(S4). 이것은 원본 레포를 Claude Code에서 신뢰 폴더로 등록해야 시험할 수 있어, 사용자 전역 파일(`~/.claude.json`)이 바뀐다.
- **추천안**: 지금은 2차 스파이크를 돌리지 않는다.
  - S8: 취소한다(A2가 흔들리지 않았음).
  - S10: Android 단계 착수 전에 돌린다.
  - S11: 첫 버전이 Claude Code만이므로 다른 에이전트가 필요해질 때 돌린다.
  - 워크트리 신뢰 상속: 터미널로 넘기기(2차 기능)를 만들 때 함께 확인한다. 그때 원본 레포 하나를 신뢰 폴더로 등록해도 되는지 다시 묻는다.
- 물을 문장: "2차 스파이크는 지금 돌리지 않고 S8은 취소, S10은 Android 착수 전, S11은 다른 에이전트가 필요할 때로 미룰까요?"

### B5. 인스턴스에 사용자 전역 지침을 넣을지 (S1·S3·S9)

- 배경: 격리 없이 띄우면 사용자 전역 지침(`~/.claude/CLAUDE.md`: 한국어 응답, 커밋 작성자 jadewisemann, AI 표기 금지 등), 워크스페이스 `AGENTS.md`, 사용자 훅·플러그인, 커넥터 MCP가 모든 인스턴스에 들어간다. 첫 턴 비용 차이도 크다(캐시 생성 19만 vs 3천 토큰). 격리하면 이것들이 빠지고 Claude Code 기본 커밋 attribution 문구(AI 공동 작성자 꼬리줄)가 돌아온다. S3에서는 전역 지침이 새어 들어가 워커가 커밋 작성자를 바꾸고 attribution을 지웠다. 사용자 규칙을 지킨 셈이지만 봇 정의 밖에서 들어온 행동이다.
- **추천안**
  - 인스턴스는 **격리를 기본**으로 한다(`--setting-sources ""`). 사용자 전역 지침·훅·플러그인·커넥터가 들어가지 않는다.
  - 대신 사람이 정하는 **전역 규칙 파일** `policy/global-instructions.md`를 모든 봇에 넣는다. 지금 `~/.claude/CLAUDE.md`의 커밋·PR 규칙(작성자, AI 표기 금지, 이력 손대지 않기)과 응답 언어를 옮겨 둔다.
  - 정책 `--settings`에 `attribution` 값을 명시한다.
  - 이 파일은 `policy/` 아래라 자기개선이 바꾸지 못한다.
- 대안: 전역 지침을 그대로 들인다(`claudeMdExcludes` 없이 `project,local`). 간단하지만 봇 행동이 봇 정의 밖의 파일에 좌우되고 비용이 크다.
- 물을 문장: "jadecode가 띄우는 봇에는 지금 쓰시는 `~/.claude/CLAUDE.md`를 그대로 넣지 않고, 커밋 작성자·AI 표기 금지·응답 언어 같은 규칙만 `policy/global-instructions.md`로 옮겨 모든 봇에 넣을까요?"

### B6. 구독 이용률이 높을 때 무엇을 멈추나 (S1·S9, 라운드 A9)

- 배경: 모든 봇과 평가를 사용자 구독 하나로 돌린다(A9). 구독에는 계정 전체의 5시간·7일 이용률 한도가 있고, 사용자가 직접 쓰는 Claude 사용분과 jadecode가 같은 한도를 나눈다. 스파이크 다섯 개를 동시에 돌렸을 때 5시간 이용률이 0.35에서 0.5로 올랐다(S1). CLI는 `rate_limit_event`로 이용률을 가끔 알려 주지만 봇별로 나눠 주지는 않는다.
- **추천안**
  - 서버가 `rate_limit_event`의 이용률을 보이고, `policy/`에 임계를 둔다(기본: 5시간 창 70%, 7일 창 80%).
  - 임계를 넘으면 **비필수 일**(개선 카드, 평가 재실행, 한가할 때 고리)을 새로 시작하지 않는다. 일반 카드 일은 계속한다.
  - 95%를 넘으면 새 인스턴스 시작도 멈추고 사람에게 알린다. 이미 도는 턴은 끊지 않는다.
- 대안: 이용률을 보이기만 하고 멈추지 않는다(사용자가 직접 판단).
- 물을 문장: "구독 이용률이 높아지면 봇 개선·평가 같은 비필수 일부터 멈추고, 아주 높으면 새 작업 시작도 멈춘 뒤 알려 드릴까요? 기준은 5시간 창 70%·95%로 시작하려 합니다."

### B7. 선행 브랜치 위에 쌓은 카드의 기준 옮기기를 봇이 해도 되나 (Q11, 라운드 A4)

- 배경: 라운드 A4로 기본은 "선행 병합 후 시작"이고, 선행 시점을 병합 전으로 지정하면 후행 카드는 선행 브랜치 위에서 시작한다(stacked). 선행이 병합되면 후행 브랜치를 기본 브랜치 위로 옮겨야 한다(리베이스 또는 병합). 이 워크스페이스의 사용자 지침은 "브랜치 이력의 모양(병합 커밋·리베이스·커밋 개수)은 사람이 요청할 때만 손댄다"이고, SPEC은 커밋·push·Draft PR만 봇 자율로 둔다.
- **추천안**
  - 기준 옮기기는 **봇이 스스로 하지 않는다.** 선행이 병합되면 서버가 후행 카드에 배지 "기준 옮기기 필요"를 달고 오케스트레이터를 깨운다.
  - 오케스트레이터는 사람에게 한 줄로 알리고, 사람이 "옮겨"라고 하면 워커가 한다.
  - 이것을 사람 절차 기본값에 "브랜치 이력 바꾸기(리베이스·force push)"로 더한다.
- 대안: 봇이 리베이스까지 자율로 한다(Draft PR 브랜치에 한해 `--force-with-lease`). 흐름은 빠르지만 지금 사용자 지침과 어긋난다.
- 물을 문장: "선행 카드가 병합된 뒤 쌓인 카드의 기준을 옮기는 일(리베이스 등)은 봇이 하지 않고 알려만 드린 뒤 지시를 받아 하게 할까요? 그러려면 사람 절차 기본값에 '브랜치 이력 바꾸기'를 더합니다."

## 아키텍처 그릴링으로 넘길 설계 과제

사용자에게 묻지 않고 그릴링에서 설계자끼리(또는 사용자 확인만) 정할 것들이다.

- 서버 업그레이드 때 일하는 인스턴스: 한가할 때까지 미룸(기본) vs 인스턴스를 별도 감독 프로세스에 두기(herdr live handoff 참고).
- 오케스트레이터 세대 교체 기준(맥락 크기, 시간, 사람 요청)과 자동 압축과의 관계(S3 남은 의문).
- 예산 강제 방식: 다 쓰면 인스턴스를 멈추는가, 사람 절차(예산 초과)로 승인을 기다리는가.
- 개선 반영 뒤 이미 일하는 인스턴스의 처리(SPEC은 영향 없음, resume 스냅숏으로 그대로 됨 — S1), 자동 되돌림의 판정 규칙(B1 답에 따라).
- 오케스트레이터 기본 모델(S3는 sonnet·haiku만 측정).
- 권한 경로 예비(stream-json `--permission-prompt-tool stdio`)를 언제 쓸지(S2).
